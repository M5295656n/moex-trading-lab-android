# Техническое задание — MOEX Trading Lab

**Версия документа:** 1.1  
**Статус:** базовая спецификация проекта  
**Платформа:** Android  
**Стек:** Kotlin, Jetpack Compose, Room

## 1. Назначение и границы проекта

MOEX Trading Lab — самостоятельное Android-приложение для анализа Московской биржи, поиска торговых возможностей, тестирования стратегий на истории и ведения журнала сделок.

Проект не связан с MyCapital и не является продолжением или заменой старого MOEX Trade Lab v3.2. Старый прототип можно изучать как источник идей, но его код и ограничения не должны автоматически переноситься в новый проект.

Приложение формирует аналитику, расчёты и торговые идеи. Пользователь самостоятельно принимает решение и исполняет сделки.

**Запрещено:** автоматическая отправка брокерских заявок, автоматическое открытие/закрытие позиций и любое исполнение сделок без отдельного явного решения пользователя.

## 2. Основные параметры

- Платформа: Android.
- Язык: Kotlin.
- UI: Jetpack Compose.
- Локальная база данных: Room.
- Начальный экспериментальный капитал: 1 000 ₽.
- Инструменты: акции, фьючерсы и индексы Московской биржи.
- Графики: Advanced — японские свечи, объёмы, индикаторы и инструменты анализа.
- История: максимально доступная глубина по каждому инструменту, рынку и интервалу с обязательной проверкой реальной доступности.
- Основной источник рыночных данных: MOEX ISS.
- Работа с торговыми идеями: manual — пользователь самостоятельно подтверждает и исполняет сделки.

## 3. Версионирование и обновление приложения

Обязательное требование: каждая новая опубликованная версия должна иметь номер ровно на единицу выше предыдущей. Нельзя пропускать номера, повторно использовать старый номер или выпускать обновление с тем же номером.

### 3.1. Нумерация

- Android versionCode увеличивать строго на 1 относительно предыдущего опубликованного APK: 1, 2, 3, 4 и далее.
- versionName последовательно увеличивать на единицу в младшем компоненте: 1.0.0, 1.0.1, 1.0.2, 1.0.3 и далее. При изменении старших компонентов сохранять однозначную последовательность и документировать соответствие versionName и versionCode.
- Перед каждой сборкой сверять значения с последней опубликованной версией в репозитории и GitHub Releases.
- Хранить значения централизованно в Gradle-конфигурации.
- В каждом релизе фиксировать versionName, versionCode, commit SHA и список изменений.
- Не выдавать APK, пока фактические значения версии не проверены в собранном артефакте.

### 3.2. Обновление поверх установленной версии

Приложение должно обновляться установкой нового APK поверх предыдущего, без предварительного удаления приложения.

Для этого обязательно:
1. Не менять applicationId после первого выпуска.
2. Сохранять один и тот же сертификат подписи и закрытый ключ для всех релизов. Не генерировать новый signing key при обычных сборках.
3. Увеличивать versionCode ровно на 1 для каждого опубликованного обновления.
4. Не очищать пользовательские данные при обновлении.
5. Все изменения схемы Room сопровождать корректными миграциями.
6. Проверять обновление с предыдущей версии на новую, включая сохранность базы, журнала сделок, настроек и загруженной истории.
7. Если ключ подписи недоступен или сертификат не совпадает с предыдущей версией, не выдавать APK как совместимое обновление.
8. Не менять идентификатор приложения и подпись ради упрощения сборки или тестирования.

**Критерий приёмки:** новая версия устанавливается поверх предыдущей штатным Android-установщиком, сохраняет пользовательские данные и распознаётся системой как обновление.

## 4. Основные разделы приложения

Нижняя навигация:
1. **Главная** — сводка рынка, избранные инструменты, состояние данных, капитал и сигналы.
2. **Рынок** — каталог акций, фьючерсов и индексов, поиск, фильтры и карточки инструментов.
3. **Сканер** — поиск инструментов по техническим, объёмным, трендовым и волатильностным условиям.
4. **Аналитика** — графики, индикаторы, сравнения, статистика и рыночные режимы.
5. **Торговые идеи** — сигналы с обоснованием, входом, стопом, целью и оценкой риска.
6. **Журнал** — сделки, результаты, комиссии, комментарии и статистика торговли.

Дополнительные экраны: настройки, управление источниками и обновлением данных, справочник инструментов, спецификации фьючерсов, сведения о версии и диагностика качества данных.

## 5. Рыночные данные и MOEX ISS

MOEX ISS — основной источник данных. До реализации загрузчика проверять фактическую доступность отдельно для каждого рынка, инструмента и интервала.

Получать, где доступно:
- справочник инструментов и параметры торгов;
- исторические свечи OHLCV;
- текущие и последние доступные котировки;
- объёмы и обороты;
- параметры контрактов и сроки экспирации фьючерсов;
- торговые статусы и календарные ограничения;
- справочные данные индексов.

Не предполагать одинаковую глубину истории для всех инструментов и таймфреймов. Учитывать ограничения API, пагинацию, лимиты запросов, задержки публикации и доступность отдельных данных.

Для каждого набора данных сохранять:
- источник;
- инструмент и рынок;
- временной интервал;
- время получения;
- временной диапазон;
- полноту истории;
- статус актуальности;
- число и расположение пропусков;
- ошибку или причину неполноты.

Отсутствующие значения не заменять нулями. Нельзя выдавать задержанные данные за текущие. В интерфейсе показывать время последнего обновления, источник и состояние данных.

Загрузчик должен поддерживать дозагрузку недостающих участков, обновление последнего диапазона, кэширование, повторные запросы с контролем ошибок и работу с уже загруженными данными без сети.

## 6. Графики Advanced

График должен поддерживать:
- японские свечи OHLC и столбцы объёма;
- масштабирование и перемещение;
- выбор доступных таймфреймов;
- перекрестие и значения свечи;
- SMA и EMA;
- RSI, MACD, ATR, Bollinger Bands;
- VWAP только при наличии корректных исходных данных;
- горизонтальные уровни, линии тренда и пользовательские отметки;
- отметки предполагаемого входа, стопа и цели;
- сравнение динамики с выбранным индексом;
- выбор диапазона истории;
- отображение источника, задержки, статуса и полноты данных.

Индикаторы должны учитывать прогревочный период. При недостатке истории показывать недоступность расчёта, а не строить фиктивные значения.

## 7. Аналитическое ядро

Реализовать независимое от UI аналитическое ядро с едиными тестируемыми расчётами:
- SMA и EMA;
- RSI;
- MACD;
- ATR;
- Bollinger Bands;
- VWAP при наличии необходимых данных;
- определение направления и силы тренда;
- пробойные и разворотные условия;
- анализ объёмов;
- оценка волатильности;
- комбинированные стратегии и фильтры рыночного режима.

Для каждого сигнала сохранять инструмент, таймфрейм, время расчёта, использованные исходные данные, значения индикаторов, условия срабатывания и причину отмены или неактуальности.

Сигнал должен быть объяснимым: пользователь видит выполненные условия и факторы против идеи. Технический сигнал не является гарантией результата.

## 8. Особенности инструментов

### 8.1. Акции

Учитывать торговые режимы, лоты, шаг цены, ликвидность, комиссии, корпоративные события и корректировки исторических рядов на дивиденды/сплиты там, где данные доступны и это необходимо для корректного анализа.

### 8.2. Фьючерсы

Учитывать спецификацию контракта:
- шаг цены;
- стоимость шага цены;
- размер лота/контракта;
- гарантийное обеспечение;
- дату экспирации;
- вариационную маржу;
- торговую сессию и ограничения;
- особенности серии и перехода между контрактами.

Не переносить сигналы между сериями без явной логики склейки и маркировки. Не рассчитывать риск фьючерса как для акции.

### 8.3. Индексы

Поддерживать графики и аналитические расчёты индексов MOEX. Индексы использовать как самостоятельные аналитические инструменты и ориентиры для сравнения. Не предполагать, что индекс можно купить как обычную акцию.

## 9. Торговые идеи и риск-менеджмент

До публикации идеи рассчитывать:
- предполагаемую точку или условие входа;
- стоп-лосс и основание его размещения;
- цель или сценарии выхода;
- размер позиции;
- денежный риск;
- потенциальное соотношение риск/прибыль;
- комиссии и оценку проскальзывания;
- ограничения по ликвидности и доступному капиталу.

Размер позиции рассчитывать от заданного денежного риска и параметров инструмента. Для фьючерсов использовать спецификацию контракта и гарантийное обеспечение.

При капитале 1 000 ₽ учитывать минимальный лот, доступность инструмента и комиссии. Если корректная позиция не помещается в риск-бюджет, сообщать, что сделка не подходит по размеру, а не предлагать чрезмерный риск.

Не рекомендовать усреднение убыточной позиции. Не скрывать, если вход уже пропущен, соотношение риск/прибыль ухудшилось или сигнал устарел.

Приложение не отправляет заявки брокеру и не исполняет сделки.

## 10. Тестирование стратегий (Backtesting)

Backtesting должен моделировать:
- комиссии;
- проскальзывание;
- торговые часы и паузы;
- шаг цены, лотность и особенности инструментов;
- экспирации фьючерсов и смену контрактов;
- доступность капитала и гарантийное обеспечение;
- правила входа, выхода и отмены сигнала.

Запрещено использовать будущие данные при расчёте исторического сигнала (look-ahead bias). Исключить утечку данных между обучающей и тестовой выборками при оптимизации параметров. Отдельно показывать in-sample и out-of-sample результаты, если применимо.

Метрики:
- Win Rate;
- средняя прибыль и средний убыток;
- Expectancy;
- Profit Factor;
- максимальная просадка;
- количество сделок;
- суммарный результат после издержек;
- результаты по инструментам и рыночным режимам.

Сохранять параметры стратегии, диапазон и источник данных, версию алгоритма и дату расчёта для воспроизводимости.

## 11. Журнал сделок

Сохранять:
- инструмент и тип инструмента;
- стратегию и версию её параметров;
- дату и время;
- направление сделки;
- цену и объём входа;
- стоп и цель на момент входа;
- цену и время выхода;
- комиссии и проскальзывание;
- финансовый результат;
- причину входа и выхода;
- комментарии пользователя;
- связь с сигналом или backtesting, если она есть.

Поддерживать ручное внесение и редактирование фактических сделок. Плановые идеи и исполненные сделки должны быть разными сущностями и не смешиваться в статистике.

## 12. Архитектура и хранение

Предусмотреть слои:
- **UI:** Jetpack Compose, навигация, состояния экранов.
- **Domain:** бизнес-правила, модели, use cases, интерфейсы репозиториев.
- **Data:** реализации репозиториев, сетевые DTO, мапперы и источники.
- **Market Data:** MOEX ISS client, загрузчики, синхронизация, кэш и контроль качества.
- **Analysis Engine:** индикаторы, сигналы и стратегии.
- **Backtesting:** историческое моделирование и метрики.
- **Risk Engine:** расчёт размера позиции, риска и издержек.
- **Storage:** Room, DAO, entities и миграции.
- **Infrastructure:** логирование, обработка ошибок, фоновые задачи и конфигурация.

Не связывать бизнес-логику напрямую с Compose или сетевым API. Критичные финансовые и аналитические расчёты покрывать unit-тестами.

Room использовать для истории, инструментов, настроек, сигналов и журнала. Схему базы версионировать. Каждую миграцию проверять тестами перехода с предыдущих поддерживаемых схем. Не использовать destructive migration в релизной конфигурации, если она приводит к потере пользовательских данных.

## 13. Интерфейс и удобство использования

Интерфейс адаптировать под Android-смартфоны. Учитывать читаемость котировок, денежных сумм и временных меток. Отдельно показывать загрузку, ошибки, отсутствие данных и неполную историю.

Не перегружать главные экраны. Подробные параметры и диагностику размещать на соответствующих экранах. Форматировать цены и денежные суммы с корректной локалью и точностью инструмента.

## 14. Надёжность и безопасность

- Не хранить пароли и секреты в исходном коде.
- Не включать ключи подписи и токены в Git.
- Обрабатывать сетевые ошибки и ограничения API.
- Не подменять реальные данные демонстрационными без явной маркировки.
- Не показывать устаревшие котировки как актуальные.
- Фиксировать ошибки загрузки и расчётов.
- Не выполнять брокерские операции.
- Сохранять пользовательские данные между обновлениями.

## 15. Проверки и выпуск APK

Для каждого релиза:
1. Проверить, что versionCode ровно на 1 больше предыдущего опубликованного.
2. Проверить последовательное увеличение versionName.
3. Проверить неизменность applicationId.
4. Проверить сертификат подписи относительно предыдущего релиза.
5. Запустить unit-тесты, тесты Room migrations и необходимые интеграционные проверки.
6. Выполнить Release-сборку.
7. Проверить наличие APK, его версию, versionCode, подпись и размер.
8. По возможности установить APK поверх предыдущей версии и проверить сохранность данных.
9. Подготовить changelog и приложить APK к GitHub Release.

Не сообщать о готовности APK до подтверждения обязательных проверок. Если установка поверх предыдущей версии не проверялась, прямо указывать это.

## 16. Git и порядок разработки

- Разработка ведётся в отдельных feature-ветках.
- Изменения проходят через Pull Request.
- main сохраняется стабильной веткой.
- Не изменять main напрямую в ходе обычной разработки.
- Не сливать PR без явного разрешения пользователя.
- Перед изменением изучать существующий код и тесты.
- Не удалять и не ломать работающие функции.
- Не переписывать архитектуру без необходимости.
- Существенные решения фиксировать в документации.
- После существенных изменений запускать соответствующие тесты и проверку сборки.

## 18. Критерии готовности

Проект нельзя считать готовым только на основании наличия экранов или успешной компиляции.

Готовность каждого этапа подтверждается работающей реализацией, тестами соответствующих компонентов, проверкой сборки, проверкой фактических данных на рыночных этапах, отсутствием регрессий, документированным результатом и перечнем известных ограничений.

Полный релиз считается готовым, когда основные сценарии работают на реальных доступных данных, финансовые расчёты проверены, пользовательские данные сохраняются при обновлении, а APK подписан корректным ключом и прошёл проверки выпуска.
