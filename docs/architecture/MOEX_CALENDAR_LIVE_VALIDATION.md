# Проверка календаря MOEX ISS

## Документированные методы

Публичная документация MOEX описывает календарные методы:

- `/iss/calendars/stock` — календарь фондового рынка, таблица `off_days`.
- `/iss/calendars/futures` — календарь срочного рынка, таблица `off_days`.
- `/iss/calendars/stock/session` — расписание фондового рынка, таблица `session_schedule`.
- `/iss/calendars/futures/session` — расписание срочного рынка, таблица `session_schedule`.

Документация:
- https://www.moex.com/a8531
- https://www.moex.com/a2836
- https://www.moex.com/files/4qa0v882mt8xp7erfzs3bcjwxn
- https://moexalgo.github.io/docs/description/calendar-iss/

Проверки выполнялись с отключённой проверкой TLS только в диагностическом runner: runner получал self-signed certificate in certificate chain (curl error 60). Это не должно переноситься в Android-клиент.

## Что можно получить бесплатно через engine endpoints

Live-ответы `engines/{stock,futures}.json` содержат:

- `timetable`: недельное расписание из 7 строк (`week_day`, `is_work_day`, `start_time`, `stop_time`);
- `dailytable`: исключения по датам (на момент проверки 82 строки для stock и 72 для futures);
- для futures дополнительно `session_schedule` и `session_schedule.types` (13 строк расписания в live-ответе на момент проверки).

Примеры полей live-ответа:
- `dailytable`: `date`, `is_work_day`, `start_time`, `stop_time`;
- `timetable`: `week_day`, `is_work_day`, `start_time`, `stop_time`;
- futures `session_schedule`: `trade_session_date`, `boardid`, `secid`, `type`, `time_from`, `time_till`, `updatetime`.

Критически важно: `timetable` — расписание работы движка MOEX, а не расписание торгов конкретного рынка/борда. В live-ответе оба движка показывают `is_work_day=1` для всех семи дней недели; исключения и переносы содержатся в `dailytable`. Поэтому эти данные нельзя трактовать как календарь торгов акциями или фьючерсами и нельзя применять для генерации ожидаемых свечей. `session_schedule` срочного рынка в ответе содержит только 13 строк на дату запроса и не доказывает историческую полноту.

## Семантика официального календаря

- `is_traded=0`: нет торгов.
- `is_traded=1`: торговый день.
- `is_traded=null`: отсутствие значения нельзя трактовать как выходной или торговый день.
- `reason`: H — holiday; W — weekend session; N — normal; T — transferred.
- В расписании фондового рынка `tradingsession`: 0 — утренняя, 1 — основная, 2 — вечерняя, 5 — ДСВД; -999 — не предусмотрено.
- В расписании срочного рынка `time_from/time_till` документированы как datetime, а фондового — как time.

## Известные точки проверки реализации

Текущий адаптер PR #10 вызывает endpoint без суффикса `.json`, а декодер выводит имя таблицы из последнего сегмента URL. Документация называет таблицы `off_days` и `session_schedule`, а не `stock`, `futures` или `session`. Live-проверка не подтвердила JSON на этих calendar endpoints, поэтому production-адаптер нельзя включать до решения вопроса доступа и исправления table mapping.

## Текущее безопасное поведение

Календарь и expected candle schedule остаются UNKNOWN для оценки полноты свечей, пока нет проверенного расписания для конкретного рынка/борда/инструмента/таймфрейма. Не подменять отсутствие календарных данных нулевыми пропусками, общим расписанием или предположительными торговыми часами.


## Реализация ограниченного engine-календаря

В PR #11 добавлен `MoexEngineCalendarRepository`:

- читает именованные таблицы `timetable` и `dailytable` из `/iss/engines/{stock|futures}`;
- строит дневной диапазон включительно;
- применяет `dailytable` как override к недельной таблице, включая перенесённые рабочие/нерабочие даты;
- сохраняет неизвестный статус как `null`, если для даты нет достоверного значения;
- возвращает источник, endpoint, время получения и явный scope `ENGINE_OPERATIONAL_ONLY`.

Этот слой — только техническая информация о работе движка MOEX. Он не подключается к `CandleGapAnalyzer` или `MarketDataFreshnessEvaluator`, не хранится в Room и не считается календарём акций/фьючерсов. Для анализа свечей по-прежнему требуется подтверждённое расписание по конкретному рынку, board, инструменту и интервалу.

Также низкоуровневый ISS-декодер теперь принимает явное имя таблицы. Календарный адаптер запрашивает документированные `off_days` и `session_schedule`, а не пытается вывести имя таблицы из сегмента URL.


## Формат URL ISS и общий HTTP-клиент

Дополнительный live smoke test проверил те же адреса, которые формирует приложение:

- `/iss/engines/stock` и `/iss/engines/futures` без расширения вернули HTTP 200, но `application/xml`;
- те же адреса с `.json` вернули HTTP 200 и корректный JSON с `timetable` и `dailytable`.

Поэтому общий `MoexIssClient` теперь добавляет `.json` к endpoint, если расширение ещё не указано. Это исправляет формат запроса для всех ISS-таблиц, а не только engine-календаря. Диагностический workflow проверяет оба варианта, а JSON-вариант валидирует через jq.

TLS: в CI runner цепочка сертификата MOEX подменяется средой выполнения (curl error 60). `--insecure` используется только в диагностическом workflow для фиксации HTTP-ответов. В Android HTTP-клиенте проверка TLS не отключается.


## Уточнение доступа по официальной документации ALGOPACK (23.11.2026)

После первичной live-проверки сверены актуальные страницы методов ALGOPACK:

- фондовый календарь: `GET /iss/calendars/stock.json`, таблица `off_days`;
- торгуемость инструмента по режимам: `GET /iss/calendars/stock/securities/boards.json`, таблица `securities_boards`;
- расписание фондовых сессий: `GET /iss/calendars/stock/session.json`, таблица `session_schedule`;
- аналогичные методы описаны для срочного рынка.

В OpenAPI-страницах этих методов явно перечислены ответы HTTP 200 и HTTP 401. Это согласуется с live-результатом: обращение к `apim.moex.com/iss/calendars/stock.json` без токена вернуло 401. Следовательно, наличие методов в документации не означает анонимный бесплатный доступ. До получения и проверки условий авторизации не добавлять ключи/токены в приложение и не считать calendar API общедоступным.

Официальные страницы методов:
- https://moexalgo.github.io/docs/api/calendar-iss-calendars-stock/
- https://moexalgo.github.io/docs/api/calendar-iss-calendars-stock-securities-boards/
- https://moexalgo.github.io/docs/api/calendar-iss-calendars-stock-session/
- https://moexalgo.github.io/docs/api/iss-calendar-%D1%81%D1%80%D0%BE%D1%87%D0%BD%D1%8B%D0%B9-%D1%80%D1%8B%D0%BD%D0%BE%D0%BA/

### Что это означает для реализации

1. `off_days` может подтверждать торговый/неторговый статус даты на уровне рынка.
2. `securities_boards` связывает инструмент с доступными режимами торгов на конкретную дату.
3. `session_schedule` содержит интервалы и типы периодов для board/security, но интервалы аукционов, клиринга и торгов нельзя автоматически считать непрерывной свечной сессией.
4. Для акций необходимо связывать дату, инструмент и актуальный board. Если board меняется, нельзя переносить расписание одного режима на другой.
5. Для фьючерсов отдельно учитывать код контракта, board и дату; не переносить фондовую модель времени на срочный рынок.
6. Даже при успешной загрузке расписания expected candles можно рассчитывать только после отдельной проверки семантики каждого `type`, таймфрейма, границ периода и торговых пауз.
7. При 401/403, неполном ответе или отсутствии записи статус расписания остаётся UNKNOWN. Не подменять его engine timetable.

### Бесплатные публичные данные — отдельная ветка исследования

Официальная публичная страница MOEX «Таблица соответствия торгуемых ценных бумаг по режимам торгов» публикует ежедневную выгрузку состава инструментов и board, включая дату торгов и признаки допуска к дополнительным сессиям: https://www.moex.com/ru/SecuritiesListing.aspx

Эта выгрузка может быть независимым публичным источником для проверки доступности инструмента/режима на дату, но она не заменяет `off_days` и `session_schedule`: по ней нельзя восстановить точные интервалы торгов или доказать полноту ожидаемых свечей. До отдельной проверки формата, истории и доступности выгрузки она не подключается к production gap/freshness.

**Итог:** точный календарь и сессионное расписание описаны, но бесплатный анонимный доступ к соответствующим API не подтверждён. Engine calendar остаётся только операционным справочником; оценка полноты свечей для конкретного инструмента остаётся UNKNOWN без подтверждённого источника расписания.

## Повторная бесплатная live-проверка (25.11.2026)

Проверка выполнена в отдельном workflow `MOEX public calendar validation` без MOEX_TOKEN и без обращения к APIM. Для диагностического runner использован `curl --insecure` из-за self-signed certificate in chain; это не переносится в Android-клиент.

### Engine endpoints и исторические параметры

Для каждого рынка выполнены три запроса: без диапазона, с `from=2026-11-20&till=2026-11-25` и с `date=2026-11-24`. Все варианты вернули одинаковый HTTP 200 JSON:

| Движок | timetable | dailytable | session_schedule |
|---|---:|---:|---:|
| stock | 7 | 84 | отсутствует |
| futures | 7 | 74 | 7 |

Параметры `from/till` и `date` не ограничивают эти engine-таблицы: наборы и размеры таблиц остаются одинаковыми. Для stock `session_schedule` отсутствует. Для futures все 7 строк `session_schedule` относятся только к дате ответа — 2026-11-25. Следовательно, futures engine endpoint не даёт историческое расписание для диапазона, а stock engine endpoint не даёт расписание сессий вообще.

В `dailytable` присутствуют исключения начиная с 2018 года, но это overrides для рабочего окна движка, а не список фактических торгов по конкретной бумаге. Они не могут использоваться для вычисления ожидаемых свечей. Особенно опасно трактовать `timetable.is_work_day=1` как разрешение ожидать свечу по каждому инструменту.

Без токена скачан публичный файл:

- HTTP 200, `application/zip`, 1 797 173 байта на момент проверки.
- Внутри DBF `SL251126.dbf`, 148 507 активных записей.
- Поля содержат `TRADEDATE`, `BOARDID`, `SECURITYID`, а также флаги утренней, вечерней и выходной сессий.
- Снимок относится к 2026-11-25; 186 уникальных board ID, 5 239 SECID, дубликатов по ключу дата+борд+инструмент не обнаружено.
- Проверка структуры DBF и соответствия физического числа записей объявленному числу прошла.

Этот файл — полезный бесплатный дневной снимок соответствия инструментов и режимов торгов. Однако проверка подтвердила только доступность текущего снимка. Пока не доказано, что архивный индекс предоставляет полный исторический ряд таких файлов или что приложение может получить каждый прошлый торговый день. Поэтому этот ZIP нельзя использовать для ретроспективной проверки истории и нельзя считать подтверждением ожидаемого количества свечей.

### Вывод для реализации

1. Engine calendar оставляем только в scope `ENGINE_OPERATIONAL_ONLY`.
2. `/iss/calendars/*` не подключаем: реальные ответы — HTML, несмотря на HTTP 200.
3. Futures `session_schedule` из engine JSON можно использовать только как текущую диагностическую информацию после проверки типов сессий; не для исторического backtest gate.
4. SecuritiesListing ZIP рассматриваем как потенциальный источник ежедневных будущих снимков доступности board/security. До доказательства исторической полноты и правил флагов не включаем его в gap analyzer.
5. Daily history completeness для акций, фьючерсов и intraday остаётся `UNKNOWN`, если нет проверенного расписания для точного инструмента/борда/интервала.
6. Платные APIM, токены и подписки не используются. Ошибки TLS нельзя обходить в приложении; диагностический workflow отдельно отмечает эту особенность среды CI.

### Ограничения и вывод для модели данных

1. `SL.ZIP` можно рассматривать как бесплатный ежедневный снимок допуска security/board и трёх дополнительных сессий. Он не содержит фактического календаря торговых дат, времени сессий или признака наличия сделок.
2. Значение Y — допуск к соответствующей дополнительной сессии для строки security/board; это не означает, что сделка обязательно была совершена. Значение N также нельзя трактовать как отсутствие основной сессии.
3. Для хранения локальной истории снимков допустима отдельная модель наблюдений с ключом дата снимка + security + board, временем загрузки, URL/источником и статусом разбора. Пропущенный день загрузки должен оставаться явным пробелом, а не восстанавливаться задним числом.
4. Такой ряд можно использовать для проверки исторических изменений допуска к сессиям только начиная с момента фактического накопления снимков на устройстве. Он не восстановит прошлые даты, если соответствующие файлы недоступны.
5. Даже непрерывная история снимков не становится календарём ожидаемых свечей: для этого всё ещё нужны фактические даты/интервалы торгов и семантика конкретного board/session/timeframe, а также правило обработки дней без сделок.
6. DBF содержит текстовые поля с неустановленным пока кодированием (маркер кодовой страницы в заголовке равен 0); имена режимов не следует использовать для логики до отдельной проверки кодировки. Для ключей и флагов это ограничение не мешает структурному разбору.
7. Production `CandleGapAnalyzer`, Room schema и backtest history gate не менялись. Статус полноты истории остаётся `UNKNOWN`, когда нет подтверждённого расписания точного инструмента/борда/интервала.
